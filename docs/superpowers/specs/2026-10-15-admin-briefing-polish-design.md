# Admin polish (round 2): Daily Briefing coherence pass — design

Date: 2026-10-15. Status: approved by delegation. The owner waived design review, so the
decisions below are binding for the executor. Base: `main` after PR #38 (round-1 admin parity)
and the shared-pills wave
(`docs/superpowers/specs/2026-10-15-admin-shared-pills-design.md`) have merged. The page
code was verified on `feat/admin-parity`, which equals `main` after #38.

## 1. Intent

The owner tried the round-1 Briefing page (`/admin/daily-briefing`) and asked for a coherence pass.
His requests, quoted from the round-2 brief:

1. The difference between "Block order" and "Per-member block settings" is unclear: make it
   obvious or merge them. The per-member layout is ugly. The reference
   (`<marplanner-v1>/apps/web/src/features/daily-briefing-admin/BlockMatrix.tsx`: a
   blocks × weekdays matrix per member) is much better, so follow it.
2. "Generate today's briefing" makes no sense when any day can be generated or printed. Rename
   it to "Generate briefings" and give it a date.
3. Member selectors must be the shared member pills.
4. Opt-in governs the whole page. A member without the briefing enabled cannot be configured on
   any tab. Show them as disabled/opted-out with a way to opt in, instead of having opt-in live
   only on the second tab.
5. Run an independent review loop with fresh reviewer subagents over all the Daily Briefing admin
   content, checking naming, which controls live where, duplicated settings, flows between tabs,
   and empty/disabled states. Fix what they find before finishing.

Success criteria:

- Every control on the page has exactly one home.
- Each tab answers one question:
  - **Schedule**: who gets a briefing, and when.
  - **Blocks**: what a member's briefing contains, on which days.
  - **Briefings**: what was generated for a member and date, with regenerate, view and print.
- A member who is opted out cannot be configured anywhere and is always one click away from
  being turned on.
- The review loop (spec §8) ends with a fresh reviewer reporting no Critical or Important
  findings.
- `npm run check:standard` and `npm run check:aggregate-only` pass.

Server behaviour from round 1 stays as it is: weekday pause, history, manual print through the
queue, 202 while rendering, and the paused recheck at write time. **This pass is UI-only.** No
route, schema, OpenAPI or feature-FR change is needed. `POST /api/daily-briefing/generate-all`
already accepts `{date}` (`src/server/routes/daily-briefing.ts:84-158`,
`docs/api/daily-briefing/openapi.yaml` `GenerateAllInput`).

Facts that shape the design:

- **Block order is household-wide; block settings are per member.** The generator walks
  `buildEffectiveOrder(readBlockOrder())` (`src/server/modules/daily-briefing/index.ts:520`):
  the configured instances first, then every unlisted registry type appended. So "Remove" in the
  Block order card does **not** remove a block from anyone's briefing. It only moves the block to
  the end. Turning a block off is done only through per-member `enabled`/`weekdays`. The matrix
  drag already rewrites the same household order (`reorderBlockOrderByType`). The two cards are
  two editors for one setting, and one of them misleads.
- **A block row carries two settings that mean the same thing.** `enabled` and `weekdays` both
  decide whether a block prints on a day (`isActiveOnWeekday` and `if (!enabled) continue`).
  `weekdays: []` already means "never".
- **The page offers configuration for opted-out members.** The Blocks pills include every
  active child, opted in or not, so their blocks can be edited and their days paused even though
  `generateBriefing` rejects them ("not opted in"). The Preview workspace only says "Turn the
  briefing on for this member", and the toggle that does this is on another card.
- **The Printer page shows the auto-print state read-only** and links to `/admin/daily-briefing`
  with the text "Change in Daily Briefing" (`src/client/admin/printer/PrinterSettingsTab.tsx:87-133`).
  Its wording is "Auto-print after morning chores".

## 6. Empty and disabled states

## 8. Independent coherence review loop (required before the gate)

After implementation and green unit tests, the executor runs the app (seeded, port 43224) and
dispatches a **fresh** reviewer subagent with no implementation context. Its brief is the whole
Daily Briefing admin (all three tabs, both densities, Spanish and English, and the Printer
page's auto-print link). It checks naming consistency, which controls live where, duplicated
settings, flows between tabs, opted-out/disabled/empty states, and copy. It classifies findings
as Critical/Important/Minor and reads both the code and the running page, in its own browser
tab.

The executor fixes every Critical and Important finding and any Minor finding that is cheap,
then dispatches a **new** reviewer (never the same one), and repeats until a reviewer reports
zero Critical and zero Important. It stops after 5 rounds. If findings remain then, they are
listed as open in the report. Each round's findings and fixes are recorded in the report.

## 9. Out of scope

Server/API changes, repeated-instance editing, per-instance params, URL sub-routes, toasts,
moving Daily Messages under the briefing, Printer page changes (its link already lands on the
new default tab).
